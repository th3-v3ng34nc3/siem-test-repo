Adding AWS Config as a first-class SIEM source

00

Summary

Doc 1 covers the Lambda that runs in a customer's AWS account and pushes AWS Config data out. This document covers the other end: what has to exist inside ak-prod-siem so that push has somewhere correct to land.

The receiving side is built as a proper, dedicated collector template — templates/aws-config-collector-tpl/ — structured identically to the existing aws-cloudtrail-collector-tpl, not as a reuse of the simpler no-auth generic-http-tpl. That match matters: Doc 1's Lambda already sends a per-integration Basic Auth header (BASIC_USER/BASIC_PASS), and only the CloudTrail-style template actually checks it. Using the generic template would silently throw that credential away.

01

Requirements

What "AWS Config is supported" concretely has to mean, before writing any YAML:

  • R1

    Accept the push, at two layers of authentication. The endpoint must check both the tenant's shared credential (nginx) and a credential unique to this one integration (Logstash) — matching the security level every other AWS source already gets, not a weaker one.

  • R2

    Preserve the data as delivered. Strip only HTTP/Logstash bookkeeping fields (headers, version tags). Every field AWS Config put in configurationItems must still be there in Loki.

  • R3

    Tag consistently, without blowing up cardinality. A single stable label, job="awsconfig", must be attached to every line — matching the convention every other source label (cloudtrail, cloudwatch, azurelog, gcplog) already follows. Per-resource fields like resourceType or resourceId must not become Loki labels — that would create unbounded label cardinality. They stay in the log body, queryable with LogQL's | json parser instead.

  • R4

    Land in the existing store. No new database, no new Loki instance — the same multi-tenant Loki every other source already writes to, using the tenant's existing Loki credentials.

  • R5

    Be visible without extra per-tenant work. Once ingested, it must be queryable in the existing shared Grafana automatically. A dedicated dashboard is a nice-to-have, not a requirement for R5 to be met.

  • R6

    Reuse the existing secret conventions. No new Vault path shape, no new External Secrets pattern — see Section 4.

  • R7

    Fit the existing deployment mechanism. A template under templates/, rendered into mgmt/<env>/.../collectors/<integration_id>/ the same way every other collector already is.

02

Backend architecture

One pod, two containers — identical shape to every existing AWS collector. Logstash does the authentication and light cleanup; Alloy does the one thing it's ever allowed to do, which is forward already-clean JSON into Loki.

What changed from the CloudTrail pipeline, and why

type => "awsconfig" instead of "aws", so the filter branch is self-documenting rather than reused across unrelated sources. No GeoIP — AWS Config's configurationItems describe resource state, not API calls, so there's no caller IP field to enrich (unlike CloudTrail's sourceIPAddress). The azure/gcp branches present in CloudTrail's pipeline file were left out entirely, rather than copy-pasted forward into a new file that will never receive that traffic — one fewer thing to misread six months from now.

04

Secrets this needs

Nothing new. Both Vault paths already exist as conventions used by CloudTrail and CloudWatch today:

Vault pathUsed byContains
tenants/<tenant_id>/loki_tenantAlloyThe tenant's existing Loki write credentials — same ones every other collector already uses
tenants/<tenant_id>/aws/<intergation_id>/credsLogstashA per-integration username/password — this is what Doc 1's Lambda must send as BASIC_USER/BASIC_PASS

The second path is created the same way every AWS integration's credentials already are today — via create_tenant_secret() in scripts/common.sh. Whatever process hands those two values to whoever fills in Doc 1's terraform.tfvars is an onboarding concern, intentionally out of scope for this document.

Frontend — Grafana

By default, nothing needs to change. AWS Config data lands in the same Loki instance every tenant's Grafana already queries, so {job="awsconfig"} is searchable the moment the first log line arrives — same as every other source.

A small, purpose-built dashboard makes that data useful without hand-writing LogQL every time. This is provisioned exactly like the existing default loki-overview dashboard — as one more entry in the Grafana Helm chart's dashboards value:

Level 2 — k3s: prove the actual Kubernetes manifests

Once the pipeline logic is confirmed, the second level checks the real YAML from Section 3 — rendered, applied to a throwaway local cluster, with no Vault or External Secrets Operator involved. Locally, the Secrets those files would normally get from Vault are just created directly.

Why k3s instead of kind

k3s runs as a real single-binary Kubernetes distribution (its own kubelet, its own containerd) rather than Kubernetes-in-a-Docker-container, so it behaves closer to the real cluster and is easy to reach from outside the machine — useful for Doc 1's real-AWS end-to-end test, which needs a Lambda running in actual AWS to reach this cluster over the network via a tunnel. k3s ships its own default ingress controller (Traefik), but that's irrelevant here: this level deliberately skips testing httproute.yaml (see below) and reaches the Service directly, the same way it would under any other local cluster.

install k3s

export KUBECONFIG=/etc/rancher/k3s/k3s.yaml
sudo chmod 644 /etc/rancher/k3s/k3s.yaml   # so kubectl can read it as your user

kubectl create namespace tenant-canary-user

# stand in for the two ExternalSecrets - same keys, hand-created

  --namespace tenant-canary-user --from-file=pipeline.conf=./pipeline.conf

  --namespace tenant-canary-user --from-file=config.alloy=./config.alloy

# render the template's placeholders, same substitution add_*.sh would do

Level 3 — the real thing: a real AWS Lambda posting into this k3s pod

This is what makes Doc 1's "real AWS account" test actually end-to-end rather than two separately-verified halves. AWS Lambda runs inside AWS and cannot reach a laptop's localhost directly, so the k3s Service from Level 2 needs a public HTTPS URL for the real Lambda to hit. A tunnel is the simplest way to get one without touching any real AWS-hosted ingress:

expose the k3s pod publicly, temporarily
kubectl port-forward svc/aws-aws-config 9090:9090 -n tenant-canary-user &

# in a second terminal - ngrok is the simplest option (cloudflared works the same way)
ngrok http 9090

ngrok prints an HTTPS forwarding URL like https://a1b2c3d4.ngrok-free.app. That, plus the testuser/testpass credentials baked into the local pipeline.conf from Level 1, is exactly what Doc 1's terraform.tfvars needs for target_url/username/password — see Doc 1, Section 9, Level 2. Once the real Lambda in AWS posts a real AWS Config snapshot through that tunnel, it lands in the exact same local Loki this section already validated, provably having survived the exact same nginx-rewrite-equivalent path (Logstash's own auth check, the filter's field-stripping) the production Ingress would apply.

Tear the tunnel down when done

ngrok's free-tier URL is public and unauthenticated by ngrok itself — Logstash's own Basic Auth is the only thing protecting it. Stop the ngrok process (and the kubectl port-forward) as soon as the test run is finished.

—

Deferred / intentionally out of scope

  • An onboarding script (e.g. scripts/add_awsconfig.sh, mirroring add_cloudtrail.sh) to automate rendering this template for a real tenant. Straightforward to write once this template exists, but it's an operational tool, not part of the feature itself.
  • Detection/alert rules against AWS Config data. rules/common/aws.rules is written for CloudTrail-style API-call events; AWS Config's inventory/state data needs its own rule set (e.g. "S3 bucket became public," "security group opened to 0.0.0.0/0"), which is a separate body of work.
  • Deploying any of this against the real production cluster. Everything in this document was designed to be provable with Docker, k3s, and — for the real-AWS validation pass — a tunnel into that local k3s pod. No production tenant is touched.
